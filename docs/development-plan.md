# YJY Agent Runtime 开发计划

本文档记录 YJY Agent Runtime 的整体技术路线、分层边界、开发顺序和验收标准。它既是后续开发的任务表，也是判断每个阶段是否真正完成的依据。

当前目标是从零实现一个最小可用、结构清晰、可解释、可测试的 Agent Runtime。第一版采用线性 Agent Loop，通过明确的领域模型和端口协议组织代码。只有在出现固定工作流、人机审批、并行执行或多 Agent 编排等真实需求后，才考虑增加图式编排能力。

## 1. 总体架构

项目按照以下方向逐步组织：

```text
外部入口
  │
  ▼
应用层：编排一次 Agent 运行
  │
  ├── 调用领域对象表达决策和结果
  └── 通过端口使用外部能力
          │
          ▼
基础设施层：实现 LLM、工具、Session、Context 和 Trace
```

依赖方向必须保持单向：

```text
基础设施层 ──► 应用层 ──► 领域层
```

领域层不依赖应用层或基础设施层。应用层不直接依赖具体模型 SDK、数据库或命令行实现。

## 2. Agent Loop

第一版 Runtime 使用显式线性循环：

```text
接收 RunRequest
      │
      ▼
加载指定 Session
      │
      ▼
构建本轮 Context
      │
      ▼
调用 LLM
      │
      ▼
解析结构化决策
      │
      ├── FinalAnswer
      │       │
      │       ▼
      │   生成 RunResult 并结束
      │
      └── ToolCall
              │
              ▼
          查找并校验工具
              │
              ▼
          执行工具
              │
              ▼
          保存 ToolResult 和 Trace
              │
              └── 进入下一轮
```

循环必须具备以下安全边界：

- 最大循环轮次，禁止无限循环。
- 明确的终止原因，不能只返回含义模糊的字符串。
- LLM 输出解析失败时保留可诊断错误。
- 未注册工具、非法参数、工具超时和工具异常均有明确语义。
- 工具结果具有大小限制，避免 Context 无限增长。
- 所有状态读写显式携带 `session_id`。
- 不保存或展示模型私有思维链。

## 3. 分层职责

### 3.1 领域层

领域层表达 Agent Runtime 中稳定的概念、状态和不变量。

首批领域对象包括：

- `MessageRole`：受控的消息角色。
- `Message`：一条不可变消息。
- `ToolCall`：模型提出的工具调用。
- `ToolResult`：工具执行结果。
- `FinalAnswerDecision`：模型决定直接回答。
- `ToolCallDecision`：模型决定调用一个或多个工具。
- `RunRequest`：一次运行的输入。
- `RunResult`：一次运行的结构化结果。
- `TerminationReason`：受控的终止原因。

领域层负责：

- 使用明确类型表达有效状态。
- 在对象创建阶段拒绝明显非法输入。
- 保证工具调用 ID、消息角色和结果状态之间的一致性。
- 为应用层提供稳定且与基础设施无关的数据结构。

领域层不负责：

- 调用真实 LLM。
- 访问数据库或文件系统。
- 执行具体工具。
- 管理命令行参数。
- 记录具体日志。

### 3.2 应用层

应用层负责编排一次完整运行。

主要职责包括：

- 接收并处理 `RunRequest`。
- 加载当前 Session。
- 请求 Context 组件构建模型输入。
- 调用 LLM 端口取得结构化决策。
- 调用工具执行端口。
- 判断继续循环或终止。
- 生成 `RunResult`。
- 在关键阶段记录 Trace。

应用层只依赖抽象端口，例如：

- `LLMClient`
- `ToolExecutor`
- `SessionStore`
- `ContextProvider`
- `TraceRecorder`

这些端口描述应用层需要什么能力，不规定能力如何实现。

### 3.3 基础设施层

基础设施层实现应用层定义的端口。

后续实现包括：

- 真实 LLM SDK 适配器。
- Fake LLM 和测试 Stub。
- ToolRegistry 与参数校验。
- 内存 SessionStore。
- ContextBuilder 与压缩器。
- 结构化 TraceRecorder。
- CLI 入口。

基础设施异常必须保留原始语义。不能捕获所有异常后返回虚假的成功结果。

验收标准：

- 正常路径和主要边界规则均有测试。

## 5. 每个小功能的开发流程

每个独立小功能按照以下顺序完成：

1. 明确输入、输出、不变量、失败方式和验收标准。
2. 阅读相关代码和现有测试。
3. 确定最小修改范围。
4. 优先补充失败用例或领域规则测试。
5. 实现满足当前验收标准的最简单方案。
6. 运行与风险匹配的测试和静态检查。
7. 检查 `git status --short` 和待提交 diff。
8. 只暂存当前功能直接相关的文件。
9. 使用 Conventional Commits 类型前缀和中文描述创建独立提交。
10. 提交后检查工作区状态和最近提交记录。

若测试、权限、环境或外部服务存在阻塞，应记录已经完成的内容、真实验证结果和剩余问题，不得宣称功能已经完成。

## 6. 第一版明确不做的内容

- 不引入现成 Agent 框架替代核心循环。
- 不实现通用图执行引擎。
- 不提前设计分布式执行。
- 不提前设计复杂插件系统。
- 不让领域层依赖具体 LLM SDK。
- 不使用跨 Session 共享的业务状态。
- 不把 Session、Context 和压缩摘要混成一个无约束字典。
- 不使用不可控的实时模型输出作为默认单元测试依据。
- 不记录或展示模型私有思维链。

## 7. 完成定义

一个功能只有同时满足以下条件才算完成：

- 行为满足验收标准。
- 正常路径、非法输入、依赖失败和边界条件得到处理。
- 与 Session 相关的功能覆盖隔离测试。
- 测试已真实执行并通过。
- 文档与当前代码能力一致。
- 未写入敏感信息。
- 没有混入无关修改。
- 相关改动已经形成独立提交。

如果其中任一条件尚未满足，任务应保持未完成状态，并明确记录剩余工作。
