# 架构设计题：

### 第1题 agent后端的redis设计

传统的后端架构，后端是最后一层，redis核心任务就是给高频请求做加速。

但agent时代的后端架构，后端不再是最后一层了，大部分的业务逻辑被agent处理了。

在这种情况下，后端+agent框架的redis要如何设计？

> 这个问题真的非常的有意思。如果我们回到计算机本质，程序我觉得可以理解为一个State Machine，那么以前的话后端是整个计算链路的末端也就是说的最后一层。数据库持久化全局状态，然后redis在里面充当的其实是一个shadow state，因为磁盘IO太慢了，我们用内存做一层缓存，用于解决说吞吐还有低延迟和帮数据库挡一挡请求也就是保护存储。
> 但是现在agent时代控制流其实变了，业务编排下放给了我们的agent（TAO）,然后后端其实变成了类似是一个tool一样，而且延迟的量级其实也改变了，系统的瓶颈以前可能是说微秒级的业务代码和毫秒级别的数据库，但是现在LLM 我就说他第一个TTFT的时间吧起码也是秒级别的甚至说有些时候分钟的模型推理和外部的交互。
> 那其实如果后端不是最后一层了，我们要拿redis拿来做几毫秒的sql加速吗？很明显这个收益 太small了
> 那我分享一下就是我自己的一些实践：我很喜欢就是把agent 比作是操作系统，一个进程不能无限的占用CPU，同样的一个agent的思考链路也不是一次http从头到尾嘛
> Agent 面临网络抖动、模型超额、用户中途干预（HITL）、甚至长达数小时的外部轮询。这时候，Agent 需要执行类似 OS 的 Context Switch（上下文切换）
> 那我们要call stack序列化 在agent中就是 当前react 思考到第几步了？当前上下文窗口装了什么？挂起的 Tool 调用参数是什么？
> 那这个时候redis 就可以是存储agent执行断点也就是state checkpoint的中间件，我实习中也是这么做的。用redis json 或者 hash去存储agent 运行时的系列化状态树
> 当模型需要用户审批的时候，状态落入redis,设置TTL，释放工作节点进程。用户点击同意以后，任意一台后端worker从redis中resume，恢复执行上下文这样就解耦了长周期业务跟计算节点的生命周期
> LLM 是非确定性的，且随时伴随着重试机制。但真实世界是有side effects的,如果拿我做过的音乐场景来说也就是我去调用生成音乐的api 我不能调用两次，不然会浪费钱对吧
> 如果后端沦为了tool那么后端的核心职责就是保护物理世界提供可重入的确定性。Agent 在同一个 Session 内，可能因为上下文漂移反复发起相同的外部调用。Redis 的分布式锁和原子操作（SET NX EX / Lua）不再是用来防库存超卖，而是作为 **Tool Execution Guard**，确保针对同一实体状态的操作，无论 Agent 发起多少次尝试，全局只生效一次
> 传统 Redis 限流是对 IP/UID 限 QPS。而 Agent 架构下的限流是对 **TPM (Tokens per Minute)** 和 **Cost ($/min)**。利用 Redis 的滑动窗口或令牌桶算法，在 Agent 发起下一次推理或工具链调用前，进行前置的计算配额裁决，防止死循环把团队的 OpenAI 账单刷爆，这个也是一个点
> 我们以前用redis可能都是精确地KV match，但是现在redis 8,0的时候我记得他出了一个redis stack 这个可以做vector semantic cache，也就是其实我们可以把一些历史高频的prompt和agent执行结果生成的embedding存储在redis中这样也是一种方式
> 当一个复杂的业务演变成milti-agent 的时候 就比如我们开发常用的 planner agent -》 coder agent -》reviewer agent 这样在概念上是一个分布式系统内的并发线程模型，我们可以理解为每一个agent实例本质上是一个Actor，redis stream提供天然 持久化 带ack确认机制的消息队列 我还看过有一些项目实际用的是blackboard architecture 共享白板那使用redis也是可以作为这样一个载体
> 上面写了很多，我想说的是我们架构设计重点可能不再是如何让缓存跟数据库如何双写一致，这些都是八股了...我们应该转向去思考如何用redis去构建一个支持agent随时中断，快速唤醒，幂等调用工具，而且还能防止逻辑死循环的高可用的一个运行时环境吧。








### 第2题 kv cache+context

Kv cache跟context要如何组合设计，来保证agent效果和耗时都达到一个综合的最优状态？

请拿你参与过，或者深入理解的一个案例展开分析 
> 我觉得这个问题我们首先要理解：为什么Agent的Context和KV Cache是有点矛盾的关系？在我们的LLM推理系统中，延迟主要由两部分决定：第一部分是prefill，也就是TTFT阶段。这个时候是算力受限，重算会很慢。然后到了我们的decoder阶段，也就是TPO T阶段。这个阶段显存是带宽受限的。现在的推理引擎普遍都支持Prefix Caching，也就是我们的前缀缓存。只要当前请求的Prefix跟系统树形缓存中节点的Hash匹配，那么Prefill就可以跳过，延迟直接降到毫秒级。但是，我们的一个Agent运行的时候，其实对Prefix Caching不太友好。因为我看到过，在早期的时候，会有一些人把sister prom里面塞入时间戳、用户信息，或者那种每次轮询动态更新的tool列表。那么改动开头的一个token，后续所有的KV Cache全部会miss。还有，为了防止context过长，很多系统会采用扔掉最老的一轮会话，然后从左往右进行truncation。这就意味着我们的prefix其实发生了偏移，对吧？
那哈希是不是变了？哈希变了之后，我们的KV Cache命中率就直接变为0了。每一步都是非常昂贵的full prefix。还有关于Agent调用工具，它拿回来的结果，比如它去网页上抓数据，对吧？这个时候的数据是很脏的，而且很多很多。如果你全部塞到我们的Context里面，是不是我们的显存就会被冲垮？还会引起loss in the middle这样的问题，导致模型的智商变低。所以说，我们在讨论这个问题如何达到最优状态，其实就是说，在保证模型掌握高性噪比的前提下，构造出比较不可变的前缀Context布局。
> 其实这个方面我也有一些想法：首先，我们要先定义清楚结构。Context必须按更新频率从低到高分层，这样能保证我们的radix tree深度尽量深。分层顺序应该是：
1. Static system prompt
2. Frozen tool definitions
3. Task goal
4. Append only interactions history
5. 可能还有Working memory里面的内容
上面说的只是一个结构的顺序问题，还有一个状态压缩的问题：当我们的Append Only追加式日志进来之后，如果要进行压缩，怎么办？

首先，可以进行软删除，也就是Soft Masking：忽略一些中间无效的步骤，比如一些工具很长的内容，其实就可以不要了。如果要总，其实这种压缩有很多种策略。以Claude Code为例，它好像会有四五层策略；我们当时也会有好几层策略，就不展开讲了，因为策略实在太多了。

如果非要总结历史，我们其实可以不要每轮都进行滑动，而是设置阶段性checkpoint。比如每到10轮，就触发一轮重构：前9轮的pre fix是不是命中的？第10轮做一次冷重算，那么整体期望耗时仍然低于每一轮都进行重算。还有，我们其实像是一种大对象。比如在环境里read某个文件，或者查数据库，我们的select了很长很长的东西出来。那么我们不可以直接灌进context里面嘛，就可以返回原数据或者摘要句柄，给Agent提供详细的、细粒度的查询库。比如说你要grep。

  这里我觉得可以举个例子。比如一个系统调优的Agent，一开始可能使用我们的React循环。Agent跑一次我们的 `Make text`，输出了4000行编译，还有断言崩溃日志。Agent觉得上下文满了，脚本自动把最左侧的第一轮工具删掉了。每次工具输出格式不同，时间戳也随机变动。

这个时候，运行到第8步时，单步TTFT飙升到8秒以上。由于滑动窗口切断，KV Cache命中率为0。整个调试任务跑下来用了20分钟。其实就是因为无脑截断，Agent直接忘记了最开始的任务要求和已经尝试过的错误路径，导致陷入无限循环的dead loop。成功率只有18% 吧，好像是。我有点忘了，太久之前的了。如果这个地方我们要修改，该怎么改呢？

我们可以把prompt拆解为确定性的块：
1. root block：也就是全局固化部分，包括系统角色和基础Git Bash工具定义。

2. task block：也就是任务固化部分，包括当前report、当前仓库架构说明、issue描述，以及目标测试用例。

3. trace log：追加式日志，严格保证历史任务是append only的。只要Agent线性往下走，前n-1步都是KV Cache完全复用的；我们只需要为最新的action和observation计算一次增量KV Cache就可以了。

那么，针对make或者别的一些命令产生的大量终端日志怎么办？我们可以做环境捕出：捕捉到输出以后，不要直接塞入LM context，而是存入服务器临时文件，然后返回给LM一个handle。如果这么做的话，我们的LM其实就能够有比较多的注意力吧，能够关注到关键信息上。而且如果对A方案不满意，回滚到方案B，也能够完美命中方案A执行前的数节点的KV Cache。分支切换也没什么成本，也不需要预热什么的。

这样的话，它的耗时会降低很多。具体我记得好像是TTF从秒级降低到了几十毫秒。效果方面，任务提升也非常非常明显。所以说，我们context的管理要做成结构化、不可变、局部性的，像一个指令内存流。

如果把KV Cache比作只读和追加的高速缓存，那么就用操作系统的思维去规划Agent的每一次to call，对吧？这样做出来的Agent可能会跑得更快、更省成本，而且逻辑会比较清晰。这样交付给用户也会更好。


### 第3题 后端+agent异步同步机制设计

硬件对话场景，用户对于首token要求非常高，2秒内

但大部分工具的耗时都比较久，异步是不可避免的。

请问两者之间的异步机制要如何优化，有哪些需要注意的点？

> 最近我本来也想学习一下AIoT的一些知识。也想买点板子回来玩一下。其实这个如果这么想的话，有点苛刻，2秒以内。
   用户可能会停顿检测，也就是用户的话输入进去之后，可能要经过一个ASR，对吧？ASR之后还会经过一个TTS，然后留给Agent和后端处理的时间其实并不多。
   如果是我们平时随便调用一个外部API，比如调用一个天气API，网络RTT加上业务上下游的处理，有可能都已经3~5秒了，或者1.5秒了。那其实在数学上，这就是死路一条。所以我觉得，我们可以在LLM生成tool call的时候，不要等JSON完全生成完才发起调用。只要我们解析出tool name和参数，就直接去后台触发外部的工作协程。

然后我们可以用一些小模型、轻量上下文，或者规则引擎，快速先回复用户一句，再让TTS管道进行发声。这样的话，我觉得只要用户听到声音，听到“正在为您做什么什么什么”，系统就会赢得更多的时间去执行窗口，也就是赢得宝贵的2秒工作执行窗口。不过如果只这么做，那肯定也不太行。其实这个只能说是用一些只读操作，只读操作就可以直接像这样去完成。

但如果有写入呢？比如我需要把空调调高温度，这种写操作怎么办？我觉得可以直接回复：已经帮您把空调调到了多少多少度，同时后台异步发送MQTT指令。

如果后台上报离线设备执行失败了，那么可能需要有个补偿机制，就说没开启，必须不能让小概率的失败导致不使用，或者放弃使用这种首包体验。像这种硬件跟后端的交互，肯定得使用我们的WebSocket，或者用一些gRPC的流。

我们可以把session管道状态机拆分，分成三个channel：
1. 音频流，Audio stream。
2. token流，Text token stream。
3. 控制事件流，Control event stream。

后端需要维护一个以session ID和turn ID为key的并发状态机。工具完成后，不是直接唤醒线程，而是向我们的事件循环，也就是Event Loop里面投递一个Tool Execution Success Event，由状态机推进模型上下文，进行第二阶段生成。不过我觉得面试官你问的问题非常非常好。因为在并发异步里面，其实没有什么免费的午餐。你引入了异步，就会有很多问题。

比如用户随时说“帮我开下热水器”，可能这个时候我们的电话刚出来，我们就说“正在帮您开”。但这个时候还没说完，用户马上说“算了算了，不用开”。那这个时候你的机制是不是得设计一下？

你是不是得有一个取消令牌？每一次交互都带上全局自身的线程ID，一旦硬件端检测到用户打断的信号，就立即向后端发送Abort turn，直接取消。

后端这边也要做相应处理：所有挂起的异步Task必须响应，并调用Context cancel（）。这样硬件的音频Buffer就会清空，然后停止播报。

工具其实也是不可控的。比如用户第一句说：“帮我查下上海的天气。”工具A可能耗时3秒。然后用户接着第二句说：“那算了，我看一下广州的吧。”结果工具B耗时1秒钟。

那它返回什么？工具A先播报了广州的天气，过了2秒，工具A突然又返回一句：“今天上海下雨，22度。”用户会觉得：这个硬件智商是不是有问题？那这种怎么处理？可能我们得用一个单调递增的逻辑时钟：每个工具带一个版本号，然后返回结果进入状态机时，必须检验一下当前会话的latest turn ID。
还有一个问题：因为我们刚刚为了快速，可能会生成电话，已经让A准帮忙说好的，马上帮您叫谁叫谁。结果两秒以后，工具返回：“你的联系人中不存在张三。”这时候模型如果直接接盘，会吐出“张三的电话是叉叉叉，不存在这个人”，那是不是前后自相矛盾？

所以，我们的防御性垫话prompt必须经过系统防御性设计，表达动作倾向，而不是承诺事实。它应该说“正在帮您查询”，而不是“马上帮您呼叫谁谁谁”。

还有就是，当你感觉到工具异常的时候，系统注入给模型的四轮prompt必须强制追加转折指令，让模型使用天然的转折词：“哎，抱歉，我刚才找通讯录没找到张三。”

还有，也是在硬件的弱网条件下，它的断线和重连可能会有点频繁。比如用户可能在车库这种地方，设备端可能会重发请求。那么可能一个充值、关锁，或者发消息，并行情况下可能触发两次。

那是不是所有带副作用的异步two call，都必须在前端生成唯一的一个幂等键？然后后端配合Redis，确保只有一个Worker能真正下发给硬件网关，其余全部返回处理中的状态。
所以总结一下，我们可能需要：
1. 用垫话来换取宝贵的时间。
2. 用异步事件来解耦压力。
3. 用版本号和取消令牌来守住一致性。




### 第4题 Agent 的幂等性与重试设计

LLM 输出是非确定性的，工具调用可能超时。重试一次工具调用时，怎么保证不产生副作用（比如重复下单）？如何让 agent 框架感知"这个工具是幂等的"？

> 其实这个问题在我们前面的一些题目里也有说明，就是Agent的幂等性和重试怎么设计的问题。这里简单再讲一下：
LLM是一个概率性的token生成过程，底层的现实世界不允许这样的概率性发生。比如我们上面说的音乐Agent，不可能因为一个用户说“我要生成一首”，就因为重试导致生成了10首、20首，这样成本怎么划算？那么如果就是其实重重试也分两层吧。就是如果是LM不知道，然后只是框架底层因为网络的问题，那么话我们就直接重试就好啦。对吧？然后如果说是工具报错，然后抛给LM，那这种LM思考以后再生成一段to a call，那无论是哪一层重试吧，那你要消灭副作用，其实都得依靠确定性的幂等键，还有两阶段状态重试。首先，幂等键绝对不能交给LM自动生成。你不要写什么“生成一个UUID作为order id”，然后就怎么怎么样。其实服务端幂等拦截会被击穿，导致重复扣款。

所以，幂等键必须由我们的运行时框架根据上下文，或者通过一些确定性哈希来生成。对。如果是后端服务，比如订单服务，它收到请求以后，我们必须利用Redis或者数据库，做幂等去重。

比如首次接到一个幂等键，我们先set这个幂等键，然后pending，EX 60NX。如果成功，就开始下单。执行成功的话，这个key就会被换成真实的订单数据结构，比如success，order id ×××××。

那重试到达呢？如果发现状态已经是pending了，证明上个调用正在跑，直接挂起等待，或者返回一个错误，不允许第二次再写入。如果发现success呢？那直接使用之前缓存的状态，原地返回，根本不走下单逻辑。

如果是在一些金融或电商场景，我们就必须用两阶段状态机：
1. 第一阶段：reverse order，也就是返回一个unconfirmed的临时订单或不可变ID。拿到这个ID之后，即便这一阶段重复执行，生成的也是无害的待支付预留，超时也会作废。

2. 第二阶段：confirm order，也就是执行真正的结算。此时order ID已经被固化在上下文历史中，后续任何带着ID的重试都是幂等的。

那么，如何让Agent的框架感知到这个工具是幂等的呢？其实很像HTTP协议，它用GET、PUT、POST这些分类一样。那工具是不是得有自己的语义级别？比如GET和PUT是幂等的，那POST是不是幂等的？对，那么我们就可以在契约上进行设计。比如，我们可以设计幂等的level：它可能是只读的，还是有写入的；是天生幂等的，还是有完全副作用的，也就是不幂等的。当工具调用发生异常或超时的时候，框架拦截器会根据声明的不同契约，采用不同的应对机制：
1. 如果是只读操作，是不是可以直接用指数退避或者抖动重试3次？如果3次内可以成功，那就OK了。LM根本不需要知道网络抖动过，只要保证它的推理链条不被这种噪音打断就好了。

2. 如果是不幂等的操作，就不能静默重试，必须阻断自动循环，然后生成一个包含不确定性结果结构的observation丢给LM，告诉LM哪里有问题，再给它一个hint。

3. 如果是非幂等的工具API，在设计的时候必须配对提供。也就是这样提供了 execute_transfer()，就必须配套提供 query_transfer_status(idempotency_key)
4. 在System Pro里面也可以写明：如果任何带有修改性质的操作返回了tan out或者unknown，我们就不要进行重试操作。你的下一步是调用对应的查询工具验证状态，这一步我觉得也要写清楚。

[Runtime 拦截器识别 Tool Contract]
          │
          ├── [Case A: READ_ONLY / IDEMPOTENT]
          │        │
          │        └──> 底层自动透明重试 (Backoff Retry) ──> 成功返回结果
          │
          └── [Case B: NON_IDEMPOTENT]
                   │
                   ├──> 1. 运行时生成确定性 Idempotency-Key
                   ├──> 2. 下发工具调用 (带 Key)
                   │
                   ▼ (发生超时 Timeout)
        [拦截器拒绝静默重试]
                   │
                   └──> 返回结构化状态 `TIMEOUT_UNKNOWN`
                               │
                               ▼
        [LLM 认知感知到状态不确定]
                               │
                               └──> LLM 采取安全操作：调用 `query_status(key)` 进行状态探查
```
所以总结一下：我们在这种不可控的节点中间，用契约和状态机进行预防；我们运行时框架会进行底线防御。

要把这种副作用工具的幂等都做成类型元数据，然后把幂等键变成确定性哈希。这样的话，A准在生产环境或者复杂网络面前，也不会有什么太大的问题。



  

### 第5题 agent与后端数据的一致性设计

传统后端的数据存储都是放在后端。

但agent时代，大部分业务逻辑放到agent，后端的角色发生了变化，数据很容易变成agent存一份，后端存一份

要如何设计？



> 这个问题的话，数据变成agent的存一份，我理解的意思是直接把Context作为数据库吗？但实际上，它在操作系统上可能只是一个带着噪音、容量很小、随时可能发生数据截断的CPU寄存器吧。对。如果是这样的话，其实就有一个双写问题，还有缓存一致性问题。
  像这种问题如何设计呢？我觉得有一个底线吧。就是说，什么是我们的source of truth，也就是事实源？我觉得一般后端数据库才应该是唯一的事实源。所有业务实体，比如用户积分、订单状态、购物车、库存，都应该存在后端数据库里。

至于Agent的context，你可以把它理解成一个内存，或者说一个working空间。它是为了完成当前推理任务而投影的只读快照，也是推理过程中的中间草稿。

只要我们建立了这个原则，Agent和后端就不再是对等存储的关系，而是计算单元和外部存储的关系。
我们不能让Agent以为自己修改了状态，然后在Context里面直接宣布自己“OK，我做完了，我生成歌曲了”，这种肯定是不行的。

Agent想要修改任何状态，必须调用后端工具进行落地。如果是在多端状态下，比如用户同时在APP端操作，后台还有定时任务在跑，那么Agent读到的数据快照可能已经过期了。因此，后端返回给Agent的数据必须带版本号，或者带逻辑时钟。这样的话，当Agent发起修改工具调用时，必须强行传回版本号，后端就可以校验了。

如果用户自己刚刚在APP上改过，工具直接抛出异常。如果Agent感知到版本冲突，它就会自己再调用一次read操作，读到最新状态，然后再做出决策。这样就可以杜绝Agent基于很旧的历史盲目覆盖数据的问题。
当然，还有会话一开始时，A准不是会把用户的全部资产、订单消息和历史偏好变成一堆JSONL，然后全部塞入我们的system prompt里吗？这样也会很浪费token，还会冲垮我们的KV cache。

这个时候，这部分数据马上就变成了不可维护的静态副本。所以我们首先要做数据据饼化，也就是在context里只放精简的元数据和ID，比如一些订单消息，直接写出来就好了，详细信息再让他调用工具去查，这样会好很多。

还有，有一些数据有时效性，只有当Agent产生推理意图时，才会触发对应的工具去拉取最新的只读片段。拉取完之后，不应该长时间留在上下文的细节里，可以通过我们的Summarization进行压缩，或是依靠上下文滚动，把它划弄出去。这就是各种回到我们前面讲的压缩策略。
其实这个问题问得也挺好的吧，它引申到了大模型的一个数据分层模型。

1. 内层：可能是我们的COT思维链，或者一些中间意图、计算中间值。
2. 中层：可能是Redis，存储我们的对话轮次这种数据和目标类型。
3. 长期认知层：也就是用户长期画像，或者RAG这种内容。
4. 业务领域层：也就是Domain的一层，比如用户、库存、设备状态这些。

这些应该放到我们的后端去处理。我们得先理清楚这种分层，才能确保不会乱。

### 第6题 滑动窗口限流


设计一个接口限流器。可以先写单机，再说明怎么做成多机。

  

要求：

1. 按 userId 限流：任意连续 windowSeconds 秒内，每个用户最多 limit 次请求
   
2. 方法：bool allow(String userId)，返回是否放行
   
3. 必须是滑动窗口，不是固定窗口
   
4. 不活跃用户的数据要能清理，避免内存一直涨
   

需要回答：

1. 用什么数据结构，核心逻辑怎么写（伪代码或任意语言）
   
2. 时间、空间复杂度
   
3. 固定窗口、滑动窗口、令牌桶、漏桶分别适合什么场景
   
4. 如果用 Redis 做集群限流，key、数据结构和原子操作怎么设计
   

> 首先，滑动窗口的本质像是拿了一把尺子，在时间轴上划。不管你什么时候发来请求，尺子的右端永远对准当前时间，然后数一下这个范围内有多少个请求。如果超过limit，就直接拦截，然后报错什么的。具体实现的话：
1. 数据结构：要考虑怎么存时间。可以用一个双端队列，deque<long> 来存储时间戳，最新的放在队尾，超过的从队头出去。

2. 多线程并发：肯定不能加一把大锁，因为所有用户抢一把锁，系统就会很慢，几乎不可用。一个人可能就阻挡了一堆人。所以要对每一个user id进行分段加锁。

3. 不活跃用户删除：采用被动清除和主动清除结合。被动清除是用户每次来的时候，都要清空过期时间戳；主动清除是用户只访问一次就不来了，队列虽然是空的，但User Map的Key还在，所以必须有守护后台线程定期清理超时的Key

4. 存储：用户信息会使用Concurrent HashMap。因为每个用户都要维护一个记录历史请求时间戳的队列。对



```java
import java.util.ArrayDeque;
import java.util.Deque;
import java.util.concurrent.*;
import java.util.concurrent.locks.ReentrantLock;

public class SlidingWindowRateLimiter {
    private final long windowMs; // 窗口时长（毫秒）
    private final int limit;     // 窗口内最大请求数

    // 内部类：维护单个用户的滑动状态
    private static class UserBucket {
        final Deque<Long> deque = new ArrayDeque<>();
        final ReentrantLock lock = new ReentrantLock(); // 单用户独立锁
        volatile long lastAccessTime = System.currentTimeMillis(); // 记录最后访问时间，供GC使用
    }

    // 存放所有用户的映射
    private final ConcurrentHashMap<String, UserBucket> userMap = new ConcurrentHashMap<>();
    
    // 定时清理不活跃用户的后台线程池
    private final ScheduledExecutorService cleanScheduler = Executors.newSingleThreadScheduledExecutor(r -> {
        Thread t = new Thread(r, "RateLimiter-Cleaner");
        t.setDaemon(true); // 设为守护线程，JVM退出时不阻塞
        return t;
    });

    public SlidingWindowRateLimiter(int windowSeconds, int limit) {
        this.windowMs = windowSeconds * 1000L;
        this.limit = limit;

        // 启动后台清理任务：每隔 windowSeconds 执行一次清理
        cleanScheduler.scheduleAtFixedRate(this::cleanInactiveUsers, windowSeconds, windowSeconds, TimeUnit.SECONDS);
    }

    /**
     * 核心判断方法
     */
    public boolean allow(String userId) {
        long now = System.currentTimeMillis();
        long boundary = now - windowMs; // 窗口左边界

        // 1. 获取或创建该用户的状态桶（线程安全）
        UserBucket bucket = userMap.computeIfAbsent(userId, k -> new UserBucket());

        // 2. 锁住当前用户，避免并发冲突
        bucket.lock.lock();
        try {
            bucket.lastAccessTime = now;
            Deque<Long> deque = bucket.deque;

            // 3. 淘汰过期数据：把落在窗口左边界之外的时间戳全部移出队列
            while (!deque.isEmpty() && deque.peekFirst() <= boundary) {
                deque.pollFirst();
            }

            // 4. 判定容量
            if (deque.size() < limit) {
                deque.addLast(now); // 记录当前请求时间
                return true;        // 放行
            }
            return false;           // 限流拦截
        } finally {
            bucket.lock.unlock();
        }
    }

    /**
     * 清理长期不活跃的用户，防止 Map 无限膨胀爆内存 (要求 4)
     */
    private void cleanInactiveUsers() {
        long now = System.currentTimeMillis();
        // 如果一个用户超过 2 个窗口周期都没请求了，说明已离线，销毁其状态
        long expireTime = now - (windowMs * 2);

        userMap.forEach((userId, bucket) -> {
            // tryLock 避免和正在请求的线程争抢导致阻塞
            if (bucket.lastAccessTime < expireTime && bucket.lock.tryLock()) {
                try {
                    // 二次检查（Double Check），确保拿到锁后确实过期了
                    if (bucket.lastAccessTime < expireTime) {
                        userMap.remove(userId, bucket); // 只有当 map 里的 value 还是当前的 bucket 才移除
                    }
                } finally {
                    bucket.lock.unlock();
                }
            }
        });
    }
}
```

```lua
-- KEYS[1]: 限流 key，例如 "rate_limit:{userId}"
-- ARGV[1]: 当前时间戳 (毫秒)
-- ARGV[2]: 窗口大小 (毫秒)
-- ARGV[3]: 限制数量 limit
-- ARGV[4]: 唯一请求标识 (now .. ":" .. uuid)

local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
local member = ARGV[4]

local clear_before = now - window

-- 1. 移除窗口外的所有陈旧数据
redis.call('ZREMRANGEBYSCORE', key, 0, clear_before)

-- 2. 获取当前窗口内剩余的请求总数
local current_requests = redis.call('ZCARD', key)

-- 3. 判断是否超过限额
if current_requests < limit then
    -- 未超限：写入当前请求
    redis.call('ZADD', key, now, member)
    -- 4. 自动垃圾清理（满足要求 4）：
    -- 每次请求顺手刷新 key 的 TTL，设为窗口的 2 倍。不活跃用户会被 Redis 原生机制自动淘汰！
    redis.call('PEXPIRE', key, window * 2)
    return 1 -- 放行
else
    return 0 -- 拦截
end
```












### 第7题 硬件主板语音流接入与 ASR 会话

  

智能硬件主板通过长连接把麦克风音频推到云端做 ASR，识别结果再交给已有的对话服务（对话服务接口已定，本题不用设计 Agent 本身）。

  

设备侧大致流程：开机鉴权 -> 建连 -> 唤醒后开始推音频 -> 说完一句话 -> 收识别结果/播报指令。

  

需要你设计云端接入接口（HTTP + WebSocket 均可，说明清楚即可），至少覆盖：

  

1. 设备鉴权与会话创建：deviceId、sn、token 怎么校验；一次“说话轮次”用什么 id 标识
   
2. 音频上行协议：帧格式（seq、timestamp、音频编码、是否最后一帧）；乱序、重复、丢包怎么处理
   
3. 断网重连：设备重连后如何恢复当前轮次，哪些数据要重传，哪些不能重复识别
   
4. 并发约束：同一 deviceId 同时只能有一个进行中的 ASR 轮次时，新请求怎么处理
   

并回答：

A. 服务端用什么数据结构保存“进行中的语音轮次”和音频帧缓冲，给出关键操作复杂度

B. 从收到首帧到输出最终识别文本的服务端处理流程（可画时序或分步骤写）



> 先回答第一道题吧。我们要设计一个云端接入入口，OK
>
> 关于这个鉴权体系：SN我刚刚用LLM查了一下，它是一个烧录在主板上的硬片出厂编号，Device ID的话，是业务分配给该硬件的逻辑实例。鉴权策略可以使用HTTP Token机制：
> 1. 开机以后，鉴权这一步由主板先调用POST请求，上传SN、Device ID、Timestamp和Nonce。
>
> 2. 再携带硬件私钥计算一个签名。
>
> 3. 云端校验通过后，签发一个带过期时间的短效JWT Token，这里面包含Device ID的声明。
>
> 4. 主板通过与云端网关建立WebSocket时，HTTP Header应该携带这个Token，格式为Authorization: <Token>。
>
> 5. 网关校验通过后，就会建立TCP/WS通道。
>
> 说话标识
> 一个说话轮次用一个标识，应该叫Turn ID。也就是说，一次唤醒到说完一句话，就是一个独立的ASR对话单元。
>
> 标识格式
> 采用分布式的单调持续ID，比如UUID V7这种东西。
>
> 生成时机
> 由设备端在首帧声明生成Turn ID。因为设备才是物理拾音的第一发现人。设备端检测到唤醒词以后，本地生成Turn ID，随后整批音频帧打上这个标记
>
> 这个音频上行协议设计的话，首先我们知道WebSocket走的是TCP，对吧？那么它其实会保证单条TCP连接内的有序性，但是断网重连、跨连接传输，还有底层的DMA缓冲调度，都会有乱序和丢包现象，所以应用层必须显式进行描述。首先，我们可以在这个帧格式里进行定义，也就是进行二进制或者Protobuf的封装。这个地方具体我搜了一下，问了一下LM，他是这么跟我说的:单帧建议大小控制在 20ms ~ 40ms 音频数据（如 16kHz, 16bit PCM 约为 640 ~ 1280 字节，非常契合 MTU）：
>
> ```
> +---------------+---------------+--------------------+---------------+
> | turnId(16B)   | seq (4B uint) | timestamp (8B uint)| codec (1B)    |
> +---------------+---------------+--------------------+---------------+
> | flags (1B)    | payloadLen(2B)| payload (PCM/Opus raw bytes...)    |
> +---------------+---------------+--------------------+---------------+
> ```
>
> - seq：当前 turnId 内从 0 开始严格单调递增的序号。
> - timestamp：硬件采集端的时间戳（毫秒），用于计算端到端拾音-上屏延迟（Jitter & Latency profiling）。
> - codec：音频编码（0: 16k16bit Mono PCM, 1: Opus, 2: Speex）。
> - flags：位掩码（Bitmask）。bit 0 (0x01): IS_FIRST_FRAME（首帧，包含采样率等元数据）bit 1 (0x02): IS_LAST_FRAME（尾帧/EOS，设备侧 VAD 检测到静音或物理按键松开）
>
> OK，后面的话，说是乱序、重复、丢包怎么处理，对吧？那么我们就可以用一些不变量。
>
> - **不变量 (Invariant)**：输入到 ASR 引擎的流必须是 seq 严格连续自增的音频帧。
> - **重复帧（seq <= last_committed_seq）**：硬件在弱网重试时可能重复推流。服务端**直接静默丢弃**。
> - **乱序到达（seq > next_expected_seq）**：放入服务端该会话的 Jitter Buffer（滑动窗口/小顶堆）。
> - **丢包/空洞（Gap）处理**：设定一个短暂的容忍窗口（如 60ms，即 3 帧的时间）。如果超时未等到空洞的 seq，为了保证交互的低延迟，**不能无限等**：触发**丢包补偿（PLC, Packet Loss Concealment）**，由服务端注入 20ms 的静音数据（PCM 0 数据包）填充空洞，递增 next_expected_seq，强行驱动 ASR 引擎，避免会话卡死。
>
> 网络中断的时候，TCP链路重置。此时设备会带着未完成的turnID来建立新的WS连接。
>
> 第一步，要恢复我们的握手流程。
>
> 接下来，我们要定义哪些重传、哪些不能重传。其实前面我们看到，可能需要维护两个指针：
> 1. 已收到的最大物理帧编号。
> 1. 已经进入ASR流引擎的单调帧编号。
> 1. **不能重复识别的数据**：凡是 seq <= asr_committed_seq 的帧，**绝对不能重新塞给 ASR 引擎**。流式 ASR 的声学模型和语言模型依赖隐状态（Hidden States），重复喂入同样的语音会导致识别出重复词（如“南南南京京大学”）。
> 4. **重传策略**：云端在 RESUME_ACK 中返回 server_acked_seq = asr_committed_seq。设备端本地环形缓冲区保留最近 2 秒的帧，收到 ACK 后，从 server_acked_seq + 1 处切片，重传未被引擎消费的数据。
>

> ### 四、 并发约束（同一设备唯一活动轮次）
>
> 主板端可能出现唤醒词连击、或者旧会话因网络延迟未完全终止，就触发了新的说话事件。
>

### 一、 架构基石：设备鉴权与会话创建

这里有两个生命周期：**连接生命周期（Connection/Session）** 和 **对话轮次生命周期（Turn）**。绝对不能把它们混为一谈。

#### 1. 鉴权体系 (`deviceId` + `sn` + `token`)
*   **物理绑定（SN）与逻辑身份（DeviceId）**：`sn` 是烧录在主板 eFuse/安全芯片里的硬件出厂序列号；`deviceId` 是业务分配给该硬件的逻辑实例。
*   **鉴权策略**：
    *   **开机换票（HTTP Token 机制）**：开机后，主板先调用 `POST /api/v1/auth/token`，上传 `deviceId`, `sn`, `timestamp`, `nonce`，并携带硬件私钥计算的 HMAC-SHA256 签名。
    *   云端校验通过后，签发一个带过期时间的短效 `JWT Token`（包含 `deviceId` 声明）。
    *   **长连接握手（WebSocket Handshake）**：主板与云端网关建立 WebSocket 连接时，在 URL Query 或 HTTP Header 中携带该 `Token`（`Authorization: Bearer <token>`）。网关校验通过，建立 TCP/WS 通道。

#### 2. 说话轮次的标识：`turnId`
一次唤醒到说完一句话，是一个独立的 ASR 会话单元。
*   **标识格式**：采用分布式单调时序 ID（如 UUIDv7，或 `deviceId_epochMs_turnSeq`）。
*   **生成方**：**由设备端生成并在首帧声明**。因为设备才是物理拾音的“第一发现人”。设备端检测到唤醒词后，本地生成 `turnId`，随后的整批音频帧都打上这个标记。

### 二、 音频上行协议设计

尽管 WebSocket 走的是 TCP，保证了单条 TCP 连接内的有序性，但**断网重连、跨连接传输、硬件底层 DMA 缓冲区调度**都会引入乱序和丢包假象。应用层协议必须显式自描述。

#### 1. 帧格式定义 (建议二进制/Protobuf 封装)
单帧建议大小控制在 20ms ~ 40ms 音频数据（如 16kHz, 16bit PCM 约为 640 ~ 1280 字节，非常契合 MTU）：

```
+---------------+---------------+--------------------+---------------+
| turnId(16B)   | seq (4B uint) | timestamp (8B uint)| codec (1B)    |
+---------------+---------------+--------------------+---------------+
| flags (1B)    | payloadLen(2B)| payload (PCM/Opus raw bytes...)    |
+---------------+---------------+--------------------+---------------+
```
*   `seq`：当前 `turnId` 内从 `0` 开始严格单调递增的序号。
*   `timestamp`：硬件采集端的时间戳（毫秒），用于计算端到端拾音-上屏延迟（Jitter & Latency profiling）。
*   `codec`：音频编码（0: 16k16bit Mono PCM, 1: Opus, 2: Speex）。
*   `flags`：位掩码（Bitmask）。
    *   `bit 0 (0x01)`: `IS_FIRST_FRAME`（首帧，包含采样率等元数据）
    *   `bit 1 (0x02)`: `IS_LAST_FRAME`（尾帧/EOS，设备侧 VAD 检测到静音或物理按键松开）

#### 2. 乱序、重复、丢包处理
*   **不变量 (Invariant)**：输入到 ASR 引擎的流必须是 `seq` 严格连续自增的音频帧。
*   **重复帧（`seq <= last_committed_seq`）**：硬件在弱网重试时可能重复推流。服务端**直接静默丢弃**。
*   **乱序到达（`seq > next_expected_seq`）**：放入服务端该会话的 Jitter Buffer（滑动窗口/小顶堆）。
*   **丢包/空洞（Gap）处理**：
    *   设定一个短暂的容忍窗口（如 60ms，即 3 帧的时间）。
    *   如果超时未等到空洞的 `seq`，为了保证交互的低延迟，**不能无限等**：触发**丢包补偿（PLC, Packet Loss Concealment）**，由服务端注入 20ms 的静音数据（PCM 0 数据包）填充空洞，递增 `next_expected_seq`，强行驱动 ASR 引擎，避免会话卡死。

### 三、 断网重连与状态恢复

网络中断时，TCP 链路重置。此时设备带着未完成的 `turnId` 建立新的 WS 连接。

#### 1. 恢复握手流程
```
Device (新连接)                            Cloud Gateway
  |                                              |
  |--- Op: RESUME_TURN (turnId, local_last_seq)-->|
  |                                              | [查找 turnId 内存上下文]
  |<-- Op: RESUME_ACK (server_acked_seq) --------|
  |                                              |
  |=== 重传 seq 从 (server_acked_seq + 1) 开始 ===>|
```

#### 2. 哪些需要重传？哪些不能重复识别？
*   **核心逻辑**：云端维护两个指针：
    1.  `recv_max_seq`：已收到的最大物理帧编号。
    2.  `asr_committed_seq`：已经喂入（Feed）流式 ASR 引擎的单调帧编号。
*   **不能重复识别的数据**：凡是 `seq <= asr_committed_seq` 的帧，**绝对不能重新塞给 ASR 引擎**。流式 ASR 的声学模型和语言模型依赖隐状态（Hidden States），重复喂入同样的语音会导致识别出重复词（如“南南南京京大学”）。
*   **重传策略**：
    *   云端在 `RESUME_ACK` 中返回 `server_acked_seq = asr_committed_seq`。
    *   设备端本地环形缓冲区保留最近 2 秒的帧，收到 ACK 后，从 `server_acked_seq + 1` 处切片，重传未被引擎消费的数据。

### 四、 并发约束（同一设备唯一活动轮次）

主板端可能出现唤醒词连击、或者旧会话因网络延迟未完全终止，就触发了新的说话事件。

*   **策略选择：打断优先（Barge-in / Latest-Wins）**

*   **并发冲突处理机制**：

        *   标记 `turnId_A` 状态为 `ABORTED`。
        *   给旧 ASR 流式推理实例发送 `Cancel` 信号，立即释放底层 GPU/CPU 推理资源。
        *   给设备端下发通知：`TurnInterrupted(turnId_A)`，让设备知晓上一个轮次已废弃。
    3.  初始化 `turnId_B` 的生命周期，绑定为该 `deviceId` 的当前唯一活跃会话。

### 回答问题 A：服务端的内存数据结构与复杂度

为了支撑高并发低延迟接入，必须避免全量深拷贝，采用轻量高效的就地调度结构。

#### 1. 数据结构设计
每个接入节点（Gateway Pod）在内存中维护两层结构：

```cpp
// 1. 设备与轮次映射表 (全局锁粒度分段)
ConcurrentHashMap<DeviceId, ActiveTurnContext*> active_turns;

// 2. 轮次上下文对象
struct ActiveTurnContext {
    string turn_id;
    TurnState state;                 // INIT, STREAMING, EOS, ABORTED
    uint32_t asr_committed_seq;     // 已经推入 ASR 引擎的 seq
    AsrClientSession* asr_stream;    // 对应的流式 ASR 引擎客户端连接 (gRPC/C-API)
    
    // 音频抖动乱序重排缓冲区 (Jitter Buffer)
    // 方案：定长环形数组 (RingBuffer) 或 基于红黑树的 Map
    std::map<uint32_t, AudioFrame> jitter_buffer; 
    
    std::mutex turn_lock;            // 保护单轮次操作的轻量互斥锁
};
```

#### 2. 关键操作的时间与空间复杂度

| 操作场景 | 采用的数据结构 | 时间复杂度 | 复杂度说明 |
| :--- | :--- | :--- | :--- |
| **设备路由查找** | `ConcurrentHashMap` | **$O(1)$** | 快速定位 `deviceId` 的当前状态 |
| **音频帧乱序插入** | `std::map<seq, Frame>` (红黑树) | **$O(\log K)$** | $K$ 为允许抖动的窗口大小（通常 $K \le 5$），几乎等价于 $O(1)$ |
| **连续帧出队消费** | 取 Map 头部连续元素 | **$O(1)$** (平摊) | 取出 `next_seq` 并喂给 ASR 引擎管道 |
| **打断抢占（抢锁清理）**| 原子指针交换 + 取消句柄 | **$O(1)$** | 仅做状态置位和资源销毁触发 |

*内存空间复杂度*：每个活动轮次只缓存极短的音频（如最大 500ms，约 16KB），会话空间复杂度为 **$O(1)$ 常数空间**。

### 回答问题 B：端到端服务端全流程

这是整个系统流转的物理图景：

```
[设备主板]            [接入网关 (Gateway)]        [流式 ASR 引擎]        [对话服务 (Agent)]
    |                         |                          |                   |
    |---- 1. 首帧(seq=0) ---->|                          |                   |
    |                         |-- 2. 鉴权 & 抢占检查 --->|                   |
    |                         |-- 3. 创建 ASR Stream --->|                   |
    |                         |-- 4. 提交音频首帧 ------->|                   |
    |                         |                          |                   |
    |---- 5. 音频帧流(seq=n)->|-- 6. JitterBuffer排序 -->|                   |
    |                         |-- 7. 连续帧送入引擎 ---->|                   |
    |                         |                          |                   |
    |                         |<-- 8. 中间文字结果 ------|                   |
    |<--- 9. 下发Partial文本--|    (用于界面/低延迟打断) |                   |
    |                         |                          |                   |
    |---- 10. 尾帧 (EOS) ---->|                          |                   |
    |                         |-- 11. 发送 EOF 信号 ---->|                   |
    |                         |<-- 12. 最终识别全量文本 -|                   |
    |                         |                          |                   |
    |                         |--- 13. 发起对话推理(HTTP/RPC) -------------->|
    |                         |<-- 14. 返回播报指令/回答 --------------------|
    |<--- 15. 下发播报指令 ---|
```

#### 分步骤详细说明：

1.  **首帧捕获与通道建立**：
    *   网关收到 `seq=0` 且含 `IS_FIRST_FRAME` 的数据包。
    *   网关校验当前设备上下文。若有进行中的老会话，直接中断（Abort）并回收资源。
    *   在内存中创建 `ActiveTurnContext`，并与后端 ASR 服务建立流式双向通信管道（如 gRPC Stream）。
2.  **音频流式中继与保序消费**：
    *   设备源源不断上传 20ms 的音频帧。
    *   网关收到帧后进入 `jitter_buffer` 排序；只要连续的 `seq` 就位，立即提取裸音频流写入 ASR gRPC Stream。
    *   ASR 引擎内部运行解码图（Decoder），期间会产生**临时结果（Partial Results）**，网关将其实时推送给设备（用于屏幕秒级上屏，提升用户主观体验）。
3.  **尾帧结算与下游分发**：
    *   设备端 VAD 检测到停顿，下发 `flags` 带有 `IS_LAST_FRAME` 的尾帧。
    *   网关收到尾帧，将缓冲区内剩余音频全部灌入 ASR 引擎，并向 ASR 管道发送输入关闭信号（Half-Close）。
    *   ASR 引擎完成最终状态搜索，返回置信度最高的**最终文本（Final Result）**。
    *   网关组装该轮次的完整上下文（`deviceId`, `turnId`, `final_text`），异步非阻塞调用已有对话服务的接口（Agent）。
    *   网关拿到 Agent 的文本/TTS 播报指令，下发给主板驱动喇叭播报。内存上下文从 `active_turns` 剔除，该轮次闭环。

### 第9题 端点检测与一轮对话状态机

- 收到有效语音帧视为说话中
  
- 连续 silenceMs 毫秒静音则认为一句话说完（端点）
  
- 从 start 起超过 maxUtteranceMs 强制结束
  
- 结束后把完整文本送给对话服务，再把播报指令发给设备
  
- 播报期间默认不监听；播报结束可自动再开听，或等下次唤醒（两种策略说明差异即可）
